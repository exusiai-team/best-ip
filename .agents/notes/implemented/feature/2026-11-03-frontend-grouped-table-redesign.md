# Agent Note: 表格重构为来源分组的两级表头 + 表头排序 + 应用壳布局

Status: implemented

## Problem

接入 [1ms IPQS](2026-11-03-ipqs-1ms-source.md) 后，表格多了三列来源不同的数据。原来的十列宽表有这些问题：

- 列名看不出来源：「评分」到底是谁的分？
- 六项 IPure 场景挤在一格里做成流式 chip，同一个场景在不同行的横向位置不对齐，只能靠「缺项显示 -1」硬撑出六格。
- 排序只能用下拉框；状态筛选看不到各状态的数量。
- 表头不吸顶，横向滚动时节点名会滚出视野。
- `main.js` 有 900 行，扫描流程、数据来源、筛选排序全混在一起，注释量远超代码量。

## Decision

- **列按来源分组**：`render.js` 的 `COLUMNS` 仍是唯一真值。每列带 `group`（net / ipqs / ipure）、`title`（脱离分组时用的完整列名）、`short`（卡片模式的标签）。两级表头由 `createHeadRows()` 生成：没有分组的列跨两行，分组列在第一行合并出来源名。每个分组的第一列画竖分隔线（`.gs`）。
- **「类型 / 原生」两列改读 1ms**（`ipqs_type` / `ipqs_native`），新增「1ms 评分」列：显示分数 + 等级，tooltip 列出扣分项，有报告地址时分数本身就是出处链接。IPure 总分同样链接到 IPure 报告。
- **IPure 六项场景拆成六个独立的 62px 子列**：天然对齐，所以缺项改为显示 `—`，只有上游明确返回的「地区受限」才显示 `-1`。这取代了[统一显示 -1](2026-09-22-frontend-next-country-column-and-unified-minus-one.md) 的做法：那个约定只是为了在流式 chip 里保持六格位置不变才存在。
- **交互**：所有分数列和「节点 / 地区」都能点表头排序（`aria-sort` 同步）；排序下拉框由 `SORTABLE_COLUMNS` 生成并与表头双向同步，卡片模式没有表头时仍然可以排序。状态筛选改为带计数的分段控件（真实 radio）；新增「住宅 / 移动」「原生」两个 1ms 快速筛选；`/` 聚焦搜索，`Esc` 清空搜索；有筛选条件时出现「清除筛选」。默认排序为 1ms 评分降序。
- **布局**：应用壳——顶部条与结果条固定，只有表格区滚动；两级表头吸顶；「排名 + 节点」两列横向冻结。`table-layout: fixed`，1440 视口下不出现横向滚动。≤900px 仍是一行一张卡片（取代[窄屏卡片流式布局](2026-09-28-frontend-narrow-card-fluid-layout.md)的版式细节）。
- **结构**：扫描流程拆到 `app/scan-ui.js`，文案常量集中到 `app/labels.js`。`main.js` 只负责数据来源、筛选排序、渲染与导出。
- **快照导出**：`staticGridHtml()` 把表头排序按钮降成纯文字、出处链接降成 span，保持「快照零外链、零可操作控件」的约定。

## Alternatives considered

### Why not 保留单格六 chip，只把缺项从 -1 改成「—」？

最强理由：改动最小，列宽不变。没有这样做，是因为流式 chip 的横向位置依赖每个 chip 的宽度，「—」与「100」宽度不同，同一场景在不同行仍然不对齐，横向比对还得先看标签。拆成独立子列之后，对齐由表格结构保证，还顺带支持按单个场景排序。

### Why not 让整页滚动、只把表头做成 sticky？

最强理由：没有嵌套滚动区。没有这样做，是因为表格容器需要 `overflow-x: auto` 才能横向滚动，而它一旦成为滚动容器，`position: sticky` 就只相对它生效，表头在整页滚动时根本吸不住。应用壳是同时满足「横向滚动 + 表头吸顶 + 首列冻结」的标准做法。

## Consequences

- 收益：每个数字都能在表头上找到出处，并能一键点开原始报告；场景列可以逐项排序和对齐比对；筛选状态与数量一眼可见。
- 代价：表格最小宽度从 1322px 变为 1380px，1440 以下的桌面视口会出现表格内横向滚动（首两列冻结，可读性不受影响）。
- 前端契约 b（index.html 的 `<thead>` 里不放控件）仍然成立：表头由 JS 生成，排序按钮只在卡片模式下随 thead 一起被裁掉，不会和 `data-label` 冲突。
